# Upgrade guide

## Upgrading from 1.x to 2.x

Version 2 changes the `entity_log_entries` table used by the bundle. The main
changes are:

### Class-level logging

`IdlabLoggable` can now be placed on an entity class to include all Doctrine-
mapped properties in change logging. Add `IdlabLoggableExclude` to a property
to exclude it:

```php
#[IdlabLoggable]
class Order
{
    #[IdlabLoggableExclude]
    private string $internalNote;
}
```

Property-level `IdlabLoggable` remains supported. An exclusion takes
precedence. Backed enum values are logged using their backing value, while
pure enum values are logged using their case name.

### Deprecated accessors

The following `EntityLogEntry` methods remain available in version 2 for
backward compatibility, but are deprecated:

| Deprecated method | Replacement |
| --- | --- |
| `getCreatedAt()` | `getLoggedAt()` |
| `getCreatedBy()` | `getUsername()` |

Update application code to use the replacement methods. The deprecated methods
may be removed in a future major version.

`EntityLogEntry` is immutable after construction in version 2. All setters
were removed, including setters for action, object identifiers, data, user
information and timestamps. Doctrine hydrates the entity without requiring
setters. Applications that modify log entries through setters must create a
new entry or update their workflow.

### Database schema update

| Version 1 | Version 2 | Notes |
| --- | --- | --- |
| `created_at` | `logged_at` | The log timestamp was renamed. |
| `created_by` | `username` | The logged-in username was renamed. |
| No column | `user_id` | A non-nullable identifier for the logged-in user. |
| Integer `object_id` | String `object_id` | Supports string and composite entity identifiers. |

The bundle does not provide migrations because the application using it owns
the database and the user table. Review and apply the schema changes as part
of the application's deployment.

> **Warning:** Version 2 explicitly maps the log entry fields to snake_case
> database columns, including `object_class`, `object_id`, `logged_at`,
> `user_id` and `impersonated_by`. This avoids differences caused by the
> consuming application's Doctrine naming strategy. Review the SQL generated
> by `doctrine:schema:update` carefully; it may propose column renames or
> drop-and-add operations when the existing schema uses different names.

#### Check the SQL generated by Doctrine

Run the schema update in a safe environment first and inspect the generated
SQL. Depending on the Doctrine DBAL version, metadata and database platform,
`doctrine:schema:update` may correctly detect a column rename and generate
statements such as:

```sql
CHANGE created_at logged_at DATETIME NOT NULL,
CHANGE created_by username VARCHAR(255) NOT NULL;
```

Do not rely on that detection. Doctrine may instead generate a drop-and-add
operation, which can destroy the existing log data. Never apply an unreviewed
`doctrine:schema:update --force` command to production.

If the generated SQL does not preserve the columns, rename them explicitly.
For MariaDB, the equivalent statements are:

```sql
ALTER TABLE entity_log_entries
    RENAME COLUMN created_at TO logged_at ,
    RENAME COLUMN created_by TO username;
```

Keep the existing column type, length, nullability and defaults if they differ
from this example. Verify the result afterwards:

```sql
SHOW COLUMNS FROM entity_log_entries;
```

#### Add and populate `user_id`

`user_id` is non-nullable in version 2. Existing rows therefore need to be
populated before the column is made `NOT NULL`. The exact table and column
names depend on the application's user entity. The following example assumes
an `users` table with an integer `id` and a unique `username`:

```sql
ALTER TABLE entity_log_entries
    ADD user_id VARCHAR(64) NULL;

UPDATE entity_log_entries AS log_entry
JOIN users AS app_user ON app_user.username = log_entry.username
SET log_entry.user_id = CAST(app_user.id AS CHAR);

SELECT log_entry.id, log_entry.username
FROM entity_log_entries AS log_entry
WHERE log_entry.user_id IS NULL;

ALTER TABLE entity_log_entries
    MODIFY user_id VARCHAR(64) NOT NULL;
```

The `SELECT` must return no rows before the final `ALTER TABLE`. If it returns
rows, resolve those usernames first. Typical causes include deleted users,
renamed usernames and historical anonymous entries. Decide how the application
wants to represent those records before enforcing the non-null constraint.

If `user_id` already exists, populate it and then change its nullability:

```sql
UPDATE entity_log_entries AS log_entry
JOIN users AS app_user ON app_user.username = log_entry.username
SET log_entry.user_id = CAST(app_user.id AS CHAR)
WHERE log_entry.user_id IS NULL;

ALTER TABLE entity_log_entries
    MODIFY user_id VARCHAR(64) NOT NULL;
```

Replace `users`, `id` and `username` with the names used by the application,
and adapt the conversion if user identifiers are UUIDs or another string type.

Back up the database and test the complete upgrade against a copy containing
realistic log data before applying it to production.
